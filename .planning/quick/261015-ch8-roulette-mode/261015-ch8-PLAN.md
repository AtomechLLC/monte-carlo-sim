## Objective

The user asked for "a Roulette simulation. Players select a number and/or color from a standard
Roulette wheel, then run 100 simulations to see how often their prediction wins (Red, Black,
Green or a number)." A follow-up asked for craps as a fourth mode afterwards, so the shell and
the two new shared pieces below are built to take a fourth game without another refactor.

Roulette joins Hold'em and Blackjack as a third entry in the game-mode switcher. The player
picks a colour (red / black / green) and/or one straight-up pocket on the layout, presses
**Spin 100**, and watches the batch land: the hit count climbs spin by spin, the observed hit
rate wobbles around the true probability, and the odds panel says how many hits the maths
expected. Another press adds 100 more, so convergence is something you watch across batches.

## Design decisions

1. **Both wheels, as the explorable variable.** A single-zero (European, 37 pockets) and a
   double-zero (American, 38) wheel, toggled from the session bar exactly where the other two
   games put their shoe size. The toggle is the roulette mirror of the deck-count control — it
   is the one parameter that changes every probability on the table, and the printed line on
   the felt states the house edge it implies (2.70% vs 5.26%). Default: single zero.

2. **The spins run on the main thread, deliberately.** CLAUDE.md forbids Monte Carlo trials
   on the main thread because 200,000 hand evaluations block the UI. A batch here is 100
   integer draws from `pure-rand` — microseconds — and it is not streamed from a worker because
   there is nothing to stream. The engine still takes an injected `RandomGenerator` so the
   frequency anchors are seeded and deterministic, and `Math.random()` is never used.

3. **The batch lands progressively, and that IS the convergence display.** `spin()` appends
   100 results synchronously; a `revealed` cursor in the store controls how many the display
   counts, and a small shared hook (`useProgressiveReveal`) advances the cursor one spin every
   24 ms (~2.4 s per batch). Under `prefers-reduced-motion` the whole batch lands at once —
   which is also what makes every jsdom test deterministic (the harness forces reduce). The
   hook is game-agnostic so craps can reuse it.

4. **Predictions are scored over the history, not baked into it.** The spins are independent
   of the prediction, so changing the prediction re-scores the same history ("what if I had
   bet black?"). Colour and number are scored as two independent targets when both are set.

5. **One scoring function for every "pick an outcome, run trials" game.**
   `engine/predictionScore.ts` turns (hits, trials, true probability, payout) into observed
   rate, expected hits and net units at one unit per trial. Roulette uses it now; craps next.

6. **Every roulette bet has the same house edge, and the test suite proves it.** Payout is
   derived as `36 / pocketsCovered − 1` (35:1 straight up, 1:1 on a colour, 17:1 on the
   American green pair), which makes `EV = (36 − N) / N` for every target — a property test,
   not a table.

7. **Table shape carries information (the Blackjack half-moon precedent).** The roulette felt is
   a rounded rectangle: wheel at the left, the classic 3 × 12 layout with its zero column to
   the right, the colour bets beneath it, and the Spin / Reset cluster floating bottom-left on
   the same `.felt-controls` plate as the other games. Pocket buttons keep the 44 px hit floor.
   Pocket colours are three new palette tokens (never the accents); the selected pocket wears a
   brass ring (a "filled picker slot" is already a brass role), never a brass fill.

8. **Store isolation, mode-shell discipline, same as Phase 5/6.** `rouletteStore` imports no
   other store. The game root reads `gameModeStore` only to pick which tree mounts. The
   restore-pending flags in `gameModeStore` generalise from "exactly a blackjack → holdem
   switch" to "any switch INTO holdem/blackjack", so a roulette → holdem switch restores the
   Hold'em table instantly rather than replaying the deal. The source-shape guard is amended in
   the same commit, per its standing rule.
