### 2.1 Phase 4 shoe primitives to both games

The DECK-01 multiset primitive is genuinely shared, not duplicated per game. `shoe.ts`

| Consumer | Phase | Call | Status |

| `src/worker/simulationApi.ts:9,56,76` and `blackjackSimulationApi.ts:10,70` | 4/6 | `shoeSize`, `cardCounts` | WIRED |

No second 52-card source, no re-derived counting loop, no value-based `Set` anywhere on
the path — `src/engine/shoePath.guard.test.ts` enforces both the `new Set(` prohibition
and (WR-04) an `.includes()` prohibition over the five shoe-path files.

### 2.2 Phase 4 streaming runner to both games' worker APIs

`createStreamingRunner` is game-generic and configured twice, never forked:

- `createSimulationApi()` — `simulationApi.ts:98`
- `createBlackjackSimulationApi()` — Blackjack config on the same runner

Both are exposed on one worker under one namespaced surface:
`Comlink.expose({ poker: ..., blackjack: ... })` (`simulation.worker.ts:10`), wrapped by a
single lazily-constructed cached handle in `workerClient.ts:74-102`. Each service owns
its own generation counter and cancels only its own namespace
(`simulationService.ts:103` calls `getApi().poker.cancel`;
`blackjackSimulationService.ts:86` calls `getApi().blackjack.cancel`). **WIRED** — a poker
cancel cannot reach a blackjack run.

Hard-crash recovery fans out to both services via `onWorkerFailure` and invalidates the
cached handle identity-guarded (`workerClient.ts:66-72`), so the next `getApi()` builds a
fresh worker. **WIRED.**

### 2.3 Store isolation (Phase 5 contract, held through Phases 6-8)

`App.tsx` is a shell with no game state — two mutually exclusive `mode ===` forks. The
only cross-game stores are `gameModeStore` (mode plus the two restore flags) and `uiStore`
(the animation gate). Confirmed by source read: `BlackjackControls.tsx` and
`blackjackStore.ts` import no Hold'em store; `gameStore`/`oddsStore`/`pickerStore` import
nothing blackjack-shaped. `App.modeShell.guard.test.ts` pins these absences at raw-source
level, and its WR-02/WR-03 amendments (path-level `../state/` pin, case-insensitive
game-name pin, recursive `src/` sweep) were falsified against real evasions in
08-VERIFICATION.

**Shared-gate audit — the seam no single phase owned.** `uiStore.pendingAnimationCount`
is shared by both games, so a mode switch mid-animation could in principle strand it and
deadlock the other game's odds effect. It cannot:

- Every `beginAnimation()` from a store action is released by that game's own `prevRef`
  effect, and each table's tracked keys cover **every** arming call site of its store —
  `TableScene.tsx:42` tracks `{dealNonce, street, revealedMask}` against `deal` /
  `advanceStreet` / `rewindStreet` / `reveal`; `BlackjackTable.tsx:47` tracks
  `{roundNonce, playerHandLength, roundPhase, revealedHole}` against `deal` / `hit` /
  `stand` / `revealHole`. Neither `setDeckCount` arms.
- Every per-card registration releases on unmount — `useAnimationGate.ts:47-55` and
  `useExitGate.ts:180-188` both release a pending unit in cleanup, so unmounting a whole
  game tree drains its units.
- `resetAnimations()` has **zero** production call sites (verified by grep) — the gate's
  correctness rests entirely on balanced accounting, as its own doc comment requires.

**WIRED.** Pinned by `App.modeSwitchRace.test.tsx:87` ("drains the gate to exactly 0").

**WR-03 — no 2-deck into the Hold'em evaluator (RETIRED in Phase 7 / 07-03): retired with
no hole.** This was the one worth attacking, since a retirement is the easiest place to

**WR-04 — shoe-path guards (claimed closed in Phase 7 / 07-03): CLOSED.**

`engine/evaluatorTwoDeck.ts`, closing the `.includes()`-membership bypass that the

## 6. Findings

### BLOCKER — none

No cross-phase connection is absent or broken. No end-to-end user flow fails to complete.

### WARNING

**W-01 — Two of five phase records cite a vacuous typecheck gate.**
`06-VERIFICATION.md` (Truth 7 and Behavioral Spot-Checks) and `07-VERIFICATION.md`
(Truth 10 and Behavioral Spot-Checks) both record `npx tsc --noEmit` exit 0 as their
type-safety evidence. That command type-checks **nothing** in this repo (solution-style
root `tsconfig.json`, `files: []` plus `references`) and passes against deliberately
broken code, so those two phases' recorded typecheck evidence is void as written. Phase 4
used `tsc -b`, Phase 5 used `npm run build` (which runs `tsc -b`), and Phase 8 correctly
flagged the vacuity and used `tsc -b`. **No live defect** — `npx tsc -b` re-run at HEAD
exits 0 — but the record is wrong in two places and should be corrected rather than
inherited by the next milestone.

**W-02 — ROADMAP Phase 8 SC3 is not literally satisfied.**
SC3 reads: *"The control follows the same 'takes effect on next deal' discipline already
established for the card picker — no disruptive mid-hand mutation."* In Hold'em,
`gameStore.setDeckCount:159-161` calls `deal()` whenever a hand is on the table. It
*forces* a deal and discards the hand, which is the opposite of "takes effect on next
deal" and is by any reading a mid-hand mutation. Phase 8 recorded this openly (08-CONTEXT
D-05, and in the executable describe-block name at
`App.deckToggleConsolidation.test.tsx:453`), and the reinterpretation is defensible — the
literal reading would regress Phase 6's shipped, verified BJ-07 mid-round re-run. But the
milestone should not carry SC3 as plainly "VERIFIED"; it is satisfied-by-interpretation,
and that qualifier belongs at milestone level rather than only inside Phase 8's artifacts.

**W-03 — DECK-04's "shows remaining-copy state" is a tooltip only.**
`src/ui/CardPicker.tsx:58-75, 120, 123`. At `deckCount === 2` with one copy consumed,
`available === 1` so `used === false`, and the button renders the bare card code with
**no visible marker and no class** — the only cue is `title="1 of 2 copies used"`. The
visible `(used)` suffix appears only once *both* copies are gone. Touch users get nothing,
and a `title` attribute is announced inconsistently across screen readers. The
requirement's plumbing is fully wired (live `deckCount` into `remainingCopies` into
disabled plus title), so this is partial delivery of the requirement's *surfacing* clause,
not a broken link.

**W-04 — Nothing proves that toggling the shoe in the running app changes the displayed numbers.**
Both DECK-02 and BJ-07 phrase the payoff as visible or verifiable *in-app*. The chain
exists in two halves that never meet:
