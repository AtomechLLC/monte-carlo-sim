# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope framing (locked by ROADMAP.md + 02-CONTEXT.md):** Phase 2 is deliberately MINIMAL/UNSTYLED. Felt table, card art, and animation are Phase 3. This contract locks **structure, layout, copy, interaction states, and accessibility** for plain semantic HTML (`<button>`, `<table>`, `<dialog>`, text) — it deliberately does NOT introduce a design system, icon library, or expanded color palette. Existing data-testids from Phase 1 are contractual and must not change: `hero-hole`, `opponents`, `trial-counter`, `win-pct`, `tie-pct`, `lose-pct`, `category-table`, `category-pct-N`.

**Autonomous mode note:** Generated inside an unattended `--auto` chain. No question below was asked interactively — every open item was resolved with the recommended default and is logged in the "Autonomous Resolution Log" section for audit.

## Layout & Component Inventory

Top-to-bottom document order (a single vertical stack, no grid/columns this phase — table-scene layout is Phase 3/TBL-01):

1. `<h1>` — "Monte Carlo Poker Simulator" (unchanged, Phase 1)
2. **Empty-hand state** (conditional — shown only when no hand has ever been dealt this session) — `data-testid="empty-hand-state"`
3. **Simulation error banner** (conditional — shown only while a worker error is active) — `data-testid="simulation-error"`
4. `DealButton` (unchanged, Phase 1 — "Deal")
5. **`CardPicker`** (NEW) — always rendered, usable before AND after a deal (picks persist per A2) — `data-testid="card-picker"`, preceded by `<h2>Card Picker</h2>`
6. **`StreetControls`** (NEW) — `data-testid` group below — preceded by `<h2>Street</h2>`. Rewind/Advance are both fully disabled (not just boundary-disabled) until a hand exists.
7. `HandDisplay` (EXTENDED) — `hero-hole` (unchanged) + `opponents` (children upgraded from `<span>` to clickable `<button>`, count still 3)
8. **`BoardDisplay`** (NEW) — `data-testid="board-cards"`, or `data-testid="board-empty-state"` at Pre-Flop — preceded by `<h2>Board</h2>`
9. `WinTieLossDisplay` (unchanged, Phase 1)
10. `OddsTable` (unchanged, Phase 1)

### Component: CardPicker

Seven slots, in this fixed order: Hero 1, Hero 2, Flop 1, Flop 2, Flop 3, Turn, River. Opponent hole cards are **never** pickable (D-07).

Each slot renders as a `<button>` whose visible text is `"{Slot Name}: {value}"` where `value` is the raw card code or `"—"` when unset, immediately followed by a `"Clear"` button (disabled when the slot is empty).

Clicking a slot button opens the 52-card panel (`<dialog>`) scoped to that slot. A single `"Clear All"` button (disabled when every slot is empty) sits after the seven slots.

### Component: 52-card panel (`<dialog data-testid="picker-panel">`)

- Heading: `"Pick a card for {Slot Name}"`
- Four suit groups, each preceded by its group heading (Clubs / Diamonds / Hearts / Spades), each containing 13 rank buttons in `ALL_RANKS` order (`2,3,4,5,6,7,8,9,T,J,Q,K,A`)
- Each card button's label is the raw card code (e.g. `"Ac"`); a used card's label becomes `"Ac (used)"` and the button is `disabled` with `title="Already used in this hand"`
- A `"Cancel"` button closes the dialog without picking (native `Escape` key and `<dialog>` backdrop click also close it — both must remain enabled, do not intercept/preventDefault on them)

### Component: StreetControls

- `"Rewind"` button — `data-testid="rewind-button"` — disabled at Pre-Flop (no earlier street) or when no hand exists
- Street name label — `data-testid="street-label"` — exact text per street: `"Pre-Flop"`, `"Flop"`, `"Turn"`, `"River"`
- `"Advance"` button — `data-testid="advance-button"` — disabled at River (no later street) or when no hand exists

### Component: BoardDisplay

Renders `board.slice(0, STREET_BOARD_COUNT[street])` as raw card-code text inside `data-testid="board-cards"` (0 cards at Pre-Flop, 3 at Flop, 4 at Turn, 5 at River). At Pre-Flop, instead render `data-testid="board-empty-state"` with the text `"No community cards yet"`.

### Component: HandDisplay (extended)

`opponents` container keeps exactly 3 children, each now a `<button type="button" data-testid="opponent-seat-{i}">` (i = 0,1,2; displayed as "Opponent 1/2/3", i.e. 1-indexed in copy, 0-indexed in testid/state):
- **Hidden (default):** visible text `"Hidden"`, `aria-label="Reveal Opponent {i+1} hole cards"`, `title="Click to reveal this opponent's hole cards"`
- **Revealed (after click, one-way — D-08):** visible text is the two raw card codes space-joined (e.g. `"Ah Kd"`), `disabled`, `aria-label="Opponent {i+1} hole cards: Ah Kd (revealed)"`

## Accessibility Contract

- **Keyboard:** every new interactive element is a native `<button>` — reachable via Tab, activatable via Enter/Space, with no custom `tabindex`/`onKeyDown` reimplementation needed.
- **Focus management:** the 52-card panel uses `<dialog>.showModal()`, which natively traps focus and restores focus to the invoking slot button on close (both on pick and on Cancel/Escape). Do not add a custom focus trap.
- **Escape/backdrop close:** must remain functional (native `<dialog>` behavior) — do not call `preventDefault()` on the dialog's `cancel` event.
- **`:focus-visible` outlines:** must remain visible (browser default or `var(--accent)` per Phase 1's existing `.counter:focus-visible` pattern in `App.css`) on every new button — no CSS reset that removes them.
- **Disabled state semantics:** every `disabled` button in this contract (used cards, boundary nav, revealed opponents, empty Clear buttons) uses the native `disabled` HTML attribute (not just a visual/CSS-only disabled look), so assistive tech announces it correctly.
- **`aria-label`s:** required specifically on opponent-seat buttons (see Layout & Component Inventory) because their visible text alone ("Hidden" / raw card codes) doesn't convey the click-to-reveal affordance or revealed status to screen-reader users.
- **Live region (recommended, not blocking):** consider `aria-live="polite"` on the `trial-counter`/`win-pct` region so screen-reader users get periodic (not per-update-spam) convergence announcements — optional this phase, do not let it block acceptance; Phase 1 did not have this either.
- **Error banner:** `simulation-error` should use `role="alert"` (or `aria-live="assertive"`) so a worker failure is announced immediately, matching D-14's "must surface visibly" requirement for both sighted and screen-reader users.
