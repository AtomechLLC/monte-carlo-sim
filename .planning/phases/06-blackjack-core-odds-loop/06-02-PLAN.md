## Phase Goal

**As a** probability explorer using the simulator, **I want to** play a full Blackjack round on its own table — deal, watch bust / dealer-outcome / EV odds converge live, hit or stand, reveal the hole card, and switch the shoe between 1 and 2 decks — **so that** I can see exactly how each new piece of information and each extra deck reshapes the numbers.

<sub>Derived from ROADMAP Phase 6's `**Goal:**` line, which is written in prose rather than user-story form. No operator input was available (standing `--auto` directive); the three slots are taken directly from that goal sentence, not invented.</sub>

<objective>
D-07's structural pre-work: extract `<HoldemGame />` out of `App.tsx` so both games become sibling components under the mode fork, amend the guard test in the same commit, and consolidate the two diverged testid safety-net arrays.

Purpose: this is the file every UI-side plan in waves 3-4 builds on, and it is the one change in the phase with a real regression surface (the shipped Hold'em path, D-08). Doing it first, alone, with zero blackjack code in the diff, means any Hold'em regression is unambiguously attributable to this plan. 05-REVIEW WR-03 already flagged the current shape as a leakage trap that would trap Phase 6; this closes it before Phase 6 walks into it.
Output: one new component, a slimmed shell, an amended guard, and one shared testid list.

**Planner decision taken under Claude's Discretion, recorded for audit — control-bar ownership.**
`06-PATTERNS.md` sketches "App.tsx keeps `<GameModeSwitcher />`". Taken literally that either splits each game component in two (its empty-state/error banner render ABOVE the control bar in the shipped DOM order, its scene row below) or reorders Hold'em's shipped DOM — both violate D-08's "Hold'em external behavior must not change". Resolution: **each game component renders its own `.control-bar` with `<GameModeSwitcher />` as its first child.** Hold'em's rendered DOM comes out byte-equivalent, the switcher stays visible in both modes with identical testids/labels/aria, and App.tsx keeps only `<MotionConfig>`, `<h1>` and the fork. Known consequence: a mode-switch click moves focus to `<body>` because the switcher's subtree identity changes. No test or UI-SPEC rule pins mode-switch focus (05-UI-SPEC A5 only forbids disabling the segments), and the shipped opponent-reveal control already accepts focus loss to body. Flagged for the phase checkpoint (06-08) to confirm no keyboard trap.

**Planner decision — temporary Blackjack shim.** `<BlackjackGame />` does not exist until plan 06-07. Until then App.tsx's blackjack branch renders `<div className="control-bar"><GameModeSwitcher /></div><BlackjackScene />` so every Phase 5 test (switcher visible in Blackjack mode, placeholder copy, DOM-absence sweeps) stays green through waves 1-3. 06-07 deletes the shim and the placeholder together.
</objective>
