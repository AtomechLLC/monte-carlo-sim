Purpose: Everything before this plan proves the code does what the code says. ENG-04 asks whether the numbers are *true*. Verified benchmark (computed during research directly against `@poker-apprentice/hand-evaluator@4.3.0` with 2,000,000 samples, not copied from a published table): **AA versus 3 random opponents — hero equity 63.83%.**

Equity versus win rate: that 63.83% figure is *equity*, which awards a fractional share of split pots. This project's `runTrials` records whole win / tie / lose counts instead. The two are related by a strict mathematical bracket — `winRate <= equity <= winRate + tieRate` — which is what makes a valid, tolerance-free-in-principle regression assertion possible without extending `runTrials`.

    (a) Sum invariants for arbitrary trial counts — generate `trialCount` with `fc.integer({ min: 1, max: 3000 })` and a `seed` with `fc.integer()`. For each generated pair, build `createRng(seed)`, hero hole from the first two entries of `FULL_DECK`, `remainingDeck = deckWithout(heroHole)`, and a `createDrawer(rng, remainingDeck, CARDS_PER_TRIAL)` draw function, then assert `categoryCounts` sums exactly to `trialCount` and `outcomes.win + outcomes.tie + outcomes.lose` equals exactly `trialCount`. Percentages that sum to 100% follow from counts that sum to the trial count; assert the counts, because that is the exact form and is not subject to floating-point tolerance.
    (b) Sampling integrity for arbitrary hero hands — generate an index pair selecting two distinct cards from `FULL_DECK` as the hero hole, wrap the drawer to capture every sample, run a modest number of trials (100 is enough — this property is about structure, not statistics), and assert that every captured sample has exactly `CARDS_PER_TRIAL` entries, that those entries are all distinct, and that no entry equals either hero hole card. Also assert `remainingDeck.length === FULL_DECK.length - 2` for every generated hero hand.

    Create `src/engine/benchmark.test.ts` with the `// @vitest-environment node` pragma on line 1. Give the suite an explicit long timeout (60000 ms) — a 200,000-trial run performs 800,000 hand evaluations and takes seconds, not milliseconds. Two cases:
    (a) AA versus 3 opponents matches the verified benchmark. Hero hole is the ace of spades and the ace of hearts. Run exactly 200,000 seeded trials against `deckWithout(heroHole)`. Compute `winRate` and `tieRate` as percentages. Assert three things: `winRate <= 63.83 + 1.0`; `winRate + tieRate >= 63.83 - 1.0`; and `winRate >= 55` as a decisive inversion floor. The first two assertions bracket the published equity from below and above using the strict `winRate <= equity <= winRate + tieRate` relation, with a 1.0 percentage-point band that is far outside the roughly 0.11 pp standard error at this trial count. The third assertion exists because a sign-inverted comparator would report a win rate near 12%, which no tolerance band should ever accommodate.
    (b) Directional sanity — with the same seed and 20,000 trials each, the win rate for AA (ace of spades, ace of hearts) is strictly greater than the win rate for 7-2 offsuit (seven of hearts, two of clubs). This needs no external reference value and fails loudly under any comparator or bucketing inversion.

The guard must never throw and must never alter the snapshot — it reports, it does not intervene, so a numeric bug surfaces during development without breaking the live convergence display. Leave production behaviour untouched.
