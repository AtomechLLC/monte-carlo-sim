## Phase Goal

ROADMAP Phase 4 goal (engine/store-only, no user-visible surface): *"The deck/shoe model correctly represents 1 or 2 physical decks — two copies of the same card are distinct, trackable objects that never collapse via value-based dedup — and the simulation streaming pipeline is generalized to serve any game, with zero behavioral drift from v1.0 at deckCount=1."*

<mvp_note>
Contract-only plan, sanctioned engine-foundation exception (see 04-01's `<mvp_note>`). This is the "worker protocol generalization" half of the phase. ARCHITECTURE.md's build order places it deliberately before any new game logic, because it is the one refactor in the milestone that has a complete pre-existing test suite as a safety net — doing it later, with Blackjack already riding on the loop, would mean refactoring subtle supersession logic under two consumers instead of one. Roadmap criterion 4 is exactly this plan's D-07 gate.
</mvp_note>

<objective>
Extract the generic streaming-Monte-Carlo machinery out of `simulationApi.ts` into `src/worker/streamingRunner.ts`, reduce `simulationApi.ts` to a Hold'em configuration on top of it, and rewrite its two deck-size assumptions to be deck-count aware — all with `simulationApi.test.ts` frozen.

Purpose: D-06 and roadmap criterion 4. `createSimulationApi` currently interleaves two separable concerns (ARCHITECTURE.md §(b)): game-agnostic streaming control flow, and Hold'em payload logic. Phase 6's Blackjack API and any future game must ride the same proven loop rather than a second, divergent copy of the run-token/throttle/yield logic — that logic is subtle enough that WR-01 was a real shipped bug fixed by switching supersession from requestId equality to object identity, and a copy-paste sibling would not inherit that fix.

Simultaneously this plan closes the two remaining single-deck assumptions in the worker: the hardcoded 52 in the length formula, and the zero-overlap assertion that ARCHITECTURE.md flags as "actively wrong, not just arithmetic" for 2 decks.

Output: `streamingRunner.ts` plus its generic test suite, and a thin `simulationApi.ts` whose frozen test file still passes byte-unmodified.
</objective>

  options?: SimulationOptions;
