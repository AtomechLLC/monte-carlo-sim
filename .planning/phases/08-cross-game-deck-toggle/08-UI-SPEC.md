# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope framing (locked by 08-CONTEXT.md D-01..D-10):** Phase 8 is a BEHAVIOR-PRESERVING consolidation — one shared deck-count segmented control extracted into `src/ui/` and rendered by BOTH `BlackjackControls` and `HoldemGame`, replacing the two shipped inline toggles. **This spec designs nothing new.** Its entire job is to pin the shared component's contract: byte-identical rendered DOM per game, the prop surface that must be expressible, and the invariance of every locked per-game toggle semantic (06-UI-SPEC A3/A4; 07-UI-SPEC A2/A3/A4). This document extends `03-UI-SPEC.md`, `05-UI-SPEC.md`, `06-UI-SPEC.md`, and `07-UI-SPEC.md`: every token, testid, and copy string from those contracts carries forward unchanged — nothing is amended here, only re-cited. **Zero new tokens, zero new classes, zero new copy, zero new accent usage, zero new choreography.**

**Autonomous mode note:** Generated inside an unattended `--auto` chain. No question was asked interactively — every gray area was resolved with the recommended default and is logged in "Defaults Chosen" below for audit.

## Shared Component: Rendered-DOM Contract (binding)

The shared component (name planner's discretion — `DeckCountToggle` per D-01's example) emits, for each game, DOM equivalent to this canonical shape (shown at count 1, no guard, no pre-click title):

```html
<div data-testid="{prefix}" role="group" aria-label="Deck count"
  ><button type="button" data-testid="{prefix}-1" aria-pressed="true">1 deck</button
  ><button type="button" data-testid="{prefix}-2" aria-pressed="false">2 decks</button
></div>
```

Binding rules (all carried from the shipped inline toggles — nothing here is new):

1. **Byte-identical per state (A2, D-06):** for every reachable state of each game, the toggle subtree's `outerHTML` is identical to what the shipped inline version rendered. Attribute order carries (wrapper: `data-testid`, `role`, `aria-label`; segments: `type`, `data-testid`, `aria-pressed`, `disabled` iff disabled, `title` iff present).
2. **Zero classes:** no `className` on the wrapper or either segment — the class list is empty today and stays empty. Styling rides the `App.css` attribute selectors (Color section).
3. **Elements:** wrapper is a `<div>`; segments are native `<button type="button">` elements. Segment labels are exactly `"1 deck"` and `"2 decks"` and NEVER change with state — `aria-pressed` alone carries which count is active (A4/D-01 "structural twin of GameModeSwitcher", carried).
4. **`aria-pressed`:** always serialized on both segments (`"true"`/`"false"`), driven by the game's own store value.
5. **`disabled`/`title`:** rendered only when supplied — an absent guard/title renders NO attribute (React's `undefined` omission), matching both shipped toggles.
6. **Active segment never `disabled`** — structurally guaranteed in both games (both guards are one-directional 2→1; see Invariance Table) and the component must not add a disabled path for the active segment.
7. **Placement unchanged:** the component renders where each inline toggle sits today — the LAST child of each game's `.control-bar` (06 Layout item 4; 07 A2). Nothing moves or reflows.

### Per-game parameterization (the complete difference surface)

| Aspect | Blackjack instance | Hold'em instance |
|--------|--------------------|-------------------|
| Testid prefix | `blackjack-deck-toggle` | `holdem-deck-toggle` |
| Active count source | `blackjackStore.deckCount` | `gameStore.deckCount` |
| Select handler | `blackjackStore.setDeckCount` | `gameStore.setDeckCount` |
| `"1 deck"` disabled when | physical-round duplicate (`hasPhysicalDuplicate` over player hand + upcard + hole + playout draws) | duplicated value in picker picks (`hasDuplicatePick`) |
| `"1 deck"` `title` | `"The dealt cards include a duplicate — impossible with one deck"` iff disabled; otherwise absent | guard title `"Your picked cards include a duplicate — impossible with one deck"` iff disabled; **else** `"Switching the shoe deals a fresh hand"` iff `deckCount === 2 && runout !== null`; otherwise absent (guard precedence per 07 A4) |
| `"2 decks"` `title` | never (no title in any state) | `"Switching the shoe deals a fresh hand"` iff `deckCount === 1 && runout !== null`; otherwise absent (07 A3 — inactive segment only, never while idle) |
| `"2 decks"` disabled | never | never |

All guard predicates and title strings are supplied BY the game call sites (each game keeps its own state wiring and guard derivation, inline or hoisted — planner's discretion per 08-CONTEXT); the component owns only the markup, the two labels, `role="group"`, and `aria-label="Deck count"`.

## Shared Component: Prop Contract (capabilities, binding; shape at planner's discretion)

The prop surface MUST be able to express, per instance (A4):

1. **Active count** (`1 | 2`) — drives both segments' `aria-pressed`.
2. **Select handler** — receives the clicked segment's count; invoked unconditionally on every segment click INCLUDING the active segment (no component-internal same-value suppression — the no-op is the store's same-value early return, carried).
3. **Per-segment disabled + explanatory `title`** — in practice only the `"1 deck"` segment is ever disabled (both guards are structurally one-directional); the component must not hard-code any title string.
4. **Testid prefix** — yields `{prefix}`, `{prefix}-1`, `{prefix}-2` exactly.
5. **Optional pre-click (idle/honesty) `title` on the inactive segment** — carries Hold'em's fresh-deal affordance on whichever segment is inactive; blackjack supplies none. When a guard title and a pre-click title would both apply to the same segment, the guard title wins (07 A4, carried).

Additional binding constraints:

- **Props-driven only (D-01):** the component reads NO store, arms NO animation gate, owns NO state. `gameStore.deckCount` and `blackjackStore.deckCount` stay exactly where they are — no shared store, no new store (store-locality invariant, carried from Phases 5/6).
- The component contains no game-specific logic — every behavioral difference in the parameterization table above arrives via props from the call site.

## Consolidation-Suite UI Assertions (SC1/SC2/SC3 — binding on planner)

One describe block per success criterion (A5), both games exercised THROUGH the shared component:

**SC1 — single shared component in both bars:**
- *Source-identity pins (A3 mechanism):* comment-stripped source of `BlackjackControls.tsx` AND `HoldemGame.tsx` each imports the shared component module and renders it; neither contains the inline segmented markup anymore; the markup literals (`aria-label="Deck count"`, segment labels, testid construction) live in exactly one `src/ui` source file.
- *Rendered-contract pins:* in each mode, the wrapper renders with the correct prefix, `role="group"`, `aria-label="Deck count"`, and `aria-pressed` reflecting THAT game's current store value ("always reflecting the active game's current deck count"). Per D-09, assert values/attributes, never mere presence.
- *Byte-identity pin (A2):* per-game `outerHTML` snapshots of the toggle subtree match the pre-extraction inline output for representative states (idle at each count; one guarded state per game; Hold'em mid-hand title state).

**SC2 — cancel + recompute, no stale numbers (D-04 — asserting shipped behavior through the shared segments, changing no logic):**
- Blackjack: mid-round toggle click → trial counter resets to 0 and every stat reads `"—"` synchronously (same frame), then the re-run streams under the new shoe (06 A3).
- Hold'em: mid-hand toggle click → `dealNonce` bumps (fresh `deal()` path), odds panel enters pending state synchronously, counter restarts from 0 (07 D-02/CR-02/D-03 chain).

**SC3 — no disruptive mid-hand mutation:** recorded satisfied-by-interpretation per 08-CONTEXT D-05 (blackjack re-runs over the SAME visible cards; Hold'em visibly replaces the hand with the full fresh-deal choreography — neither silently mutates a hand in place). The verification doc cites D-05; no UI assertion may force a literal "next deal only" reading (that would undo the locked BJ-07 findability behavior).
